# I19B 实施计划：P2P 撮合、资金冻结与限价后端

## 目标
实现可预测、不依赖前端的双边委托撮合。撮合遵循价格—时间优先、成交价和部分成交规则；把成交部分的买方资金、卖方库存和保证金从「预占」转为「待履约持有」，原子更新双方剩余数量并写成交记录。**此阶段不转移最终所有权、不写 `p2p.trade.settled`**（留 I20B）。满足 AT-05B：并发匹配同一剩余数量不会超卖、超扣或重复成交。

## 用户确认的关键决策
1. **撮合触发方式**：`create()` 只建委托；新增独立 application 用例 `OrderService.match(skuId)`，可由调用方显式触发（创建后、测试或后续定时调度）。不引入 jobs 任务（I19B checklist 未提撮合任务，撮合任务/`order.expire` 留 I22B）。HTTP 层在创建成功后调用 `match()` 作为同进程异步触发。
2. **卖单 order_fee 时机**：撮合按已成交数量立即确认。买单从预占资金中扣除已成交部分 `数量*限价 + 已成交 order_fee`（用 `captureFunds` 转为待履约/已扣减）；卖单库存转为待履约锁定，收入与 order_fee 在 I20B 履约时实际结算，但撮合要为已成交数量锁定。

## 一、纯规则：`packages/rules/src/index.ts`（新增 `order-matching/v1`）

新增 `ORDER_MATCH_RULE_VERSION = "order-matching/v1"` 与纯函数（全部整数、可重放、显式校验）：

- **`SelfTradeCheckResult`**：`{ ok: true } | { ok: false; reason: "self_trade" }`
- **`checkSelfTrade(buyerUserId, sellerUserId)`**：相同 userId 返回 self_trade。
- **`MatchLeg`**：单笔撮合结果 = `{ buyOrderId, sellOrderId, buyerUserId, sellerUserId, buyLimitPrice, sellLimitPrice, executionPrice, quantity, ruleVersion }`
- **`matchOrders(input)`**：核心纯撮合。输入 = `{ ruleVersion, now, buyOrders: MatchOrderInput[], sellOrders: MatchOrderInput[], minimumPrice }`，其中 `MatchOrderInput = { id, userId, limitPrice, remainingQuantity, createdAt, sequence }`（`sequence` 为价格-时间优先的稳定排序键，避免 createdAt 并列时不确定）。算法：
  1. 买单按 `limitPrice DESC, sequence ASC`（价格优先、时间优先）排序；卖单按 `limitPrice ASC, sequence ASC`。
  2. 维护买卖游标，逐对匹配：当 `buyLimitPrice >= sellLimitPrice` 时可成交。
  3. **成交价**：取 `max(buyLimitPrice, sellLimitPrice)` = 取**较早（ aggressor 之外）被动方价格**；这里采用「较早进入订单簿一方限价」规则——按 aggressor（后到方）发起、取 maker（先到方）限价作为成交价。等价实现：成交价 = `buyCreatedAt <= sellCreatedAt ? buyLimitPrice : sellLimitPrice`。两条委托 createdAt 相同时按 sequence 决定 maker。
  4. **成交量**：`min(buyRemaining, sellRemaining)`（部分成交）。
  5. **自成交拒绝**：buyerUserId === sellerUserId 时跳过该对（不撮合，不算成交），继续推进。
  6. 输出 = `{ ruleVersion, legs: MatchLeg[], remaining: Record<orderId, remainingQuantity> }`。**纯函数、不修改输入、可重放**。
- 校验：拒绝空/负数量、非安全整数、空 userId、未知 ruleVersion；createdAt 必须为 UTC ISO 8601。

**理由**：与现有 `openPack`/`calculateMarketQuote`/`calculateOrderFees` 同风格；规则包不依赖 DB/HTTP，撮合顺序与成交价可在单测中确定性验证。

## 二、数据库迁移：`packages/database/migrations/0020_p2p_matching.sql`（新增）

新增两张表（只追加语义，与 NPC 交易表风格一致）：

### `bilateral_trades`（成交记录，每个 MatchLeg 一行）
- `id TEXT PK`、`sku_id`、`buy_order_id`、`sell_order_id`（FK `bilateral_orders`）
- `buyer_user_id`、`seller_user_id`
- `quantity INTEGER > 0`
- `execution_price_amount INTEGER >= 0`
- `buyer_fee_amount`（买单已成交部分 order_fee，撮合时确认）
- `seller_fee_amount`（卖单已成交部分 order_fee，留 I20B 结算）
- `buyer_funds_hold_id`（指向买方新资金 hold；撮合把已成交买方资金 capture 后再以新 hold 持有待履约）
- `seller_inventory_hold_id`（指向卖方新库存 hold；撮合把卖方 inventory_holds 转为待履约）
- `seller_deposit_hold_id`（指向卖方已成交部分保证金 hold；撮合时从原保证金 hold 切出已成交部分）
- `rule_version TEXT`（`order-matching/v1`）
- `status TEXT` CHECK IN (`matched_pending_fulfillment`, `fulfilled`, `cancelled`)（I19B 只写 `matched_pending_fulfillment`；fulfilled/cancelled 留 I20B）
- `created_at`、`updated_at`
- 唯一约束：`UNIQUE(buy_order_id, sell_order_id, execution_price_amount)` 作为**撮合幂等键**，防同一对委托重复撮合生成重复成交。

### `bilateral_match_attempts`（撮合幂等/重放保护）
- `id TEXT PK`、`sku_id`、`attempt_key TEXT`（如 `match:<skuId>:<buyOrderMinSeq>:<sellOrderMinSeq>` 或调用方传入的幂等键）、`status`、`created_at`
- `UNIQUE(attempt_key)` —— 防并发撮合重放；并发第二次返回 in-progress。

实际上更稳妥的设计：撮合以**应用层乐观锁 + 单事务**保证原子，撮合幂等用 `idempotency_requests`（与 create/cancel 一致）。因此 `bilateral_match_attempts` 可省略，撮合幂等键复用 `idempotency_requests`（actor=系统/sku，key 由调用方传）。**最终采用：不新建 match_attempts 表，撮合幂等由 `idempotency_requests` + `bilateral_trades` 唯一约束双重保证。**

### 索引
- `bilateral_trades(sku_id, created_at)`
- `bilateral_trades(buy_order_id)`、`(sell_order_id)` —— 我的成交查询
- `bilateral_trades(buyer_user_id)`、`(seller_user_id)`

## 四、领域与应用：`apps/api/src/modules/orders/`

### `domain/order.ts`（修改）
- 新增常量：`MATCHED_TRADE_ENTITY_TYPE = "bilateral_trade"`、`FULFILLMENT_FUND_HOLD_REASON = "order_fulfillment"`（待履约买方资金 hold）、`MATCHED_INVENTORY_HOLD_REASON = "order"`（待履约库存，复用现有 lock 的 order_locked 通道——但需要区分「待履约」与「预占」语义，见下文）。
- 新增 `MATCHABLE_ORDER_STATUSES = new Set(["open", "partially_filled"])` 与 `isMatchable(status)`。
- 状态机说明注释更新：撮合推进 `open/partially_filled → matched_pending_fulfillment`（当 remainingQuantity 归零）或保持 `partially_filled`（仍有剩余）。

### 关键设计：卖单库存「预占 → 待履约」
现有 `inventory_holds`（卖单创建时）锁定库存为 `order_locked_quantity`。撮合把已成交部分库存转为待履约——但**不实际转移所有权**（I20B 才转给买方）。方案：撮合时对卖方原 `inventory_hold_id` 调用现有 `inventory.release` 释放已成交数量对应的 hold（减少 order_locked），**再不重新 lock**——库存「待履约」状态由 `bilateral_trades` 行 + `seller_inventory_hold_id` 关联记录表达。但这会让 order_locked 减少导致库存「看起来可用」。

**更稳妥方案**：保留已成交数量的 order_locked 不变（继续锁定），在 `bilateral_trades.seller_inventory_hold_id` 记录原 hold 引用，但需确保撤单时只释放「未成交」部分。I18B 撤单释放整个 hold——I19B 后撤单需处理部分成交。为不破坏 I18B 语义并满足「不超卖」，采用：

**最终库存方案**：撮合时**捕获**（capture）卖方原 hold 中已成交数量（`inventory.capture` 把库存从 order_locked 中实际扣减、持有量减少），把这部分库存作为「待履约」从卖方持有中扣除但**不记入买方**（暂存于 bilateral_trades 记录）。I20B 履约时再 `inventory.acquireInLedgerTransaction` 加到买方；取消时 `inventory.acquireInLedgerTransaction` 还给卖方。这样：
- 卖方持有量 = 原有 − 已成交（库存真实离开卖方可用/锁定池）
- 不会超卖（卖方可用/锁定准确）
- I18B 撤单只对未成交的 open/partially_filled 委托生效，已成交部分在 bilateral_trades 里
- `seller_inventory_hold_id` 保留原 hold 引用用于审计回溯

**买方资金方案**：买单创建时预占 `数量*限价+order_fee` 于 `fund_holds`（reason=order_buy）。撮合时：
- 对买方原 hold 调 `users.captureFunds`（扣减总额、记 debit 账本、reason=order_buy）——但 capture 是全量，部分成交需部分确认。
- 因 `captureFunds` 是全量 capture，部分成交需：**先 release 原全量 hold，再 reserve 新的「待履约 buy 资金 hold」（reason=order_fulfillment，金额=已成交数量*限价+已成交 order_fee）+ reserve 回「剩余未成交」hold（reason=order_buy）**。这保持买方预占余额不变，但把已成交部分从 order_buy 预占重新归类为 order_fulfillment 待履约。剩余委托仍可被后续撮合或撤单。
- **简化**：买方资金不实际 capture（总额、可用、冻结都不变），只是把已成交部分对应的 hold amount 从「order_buy」reason 迁移到「order_fulfillment」reason——但 fund_holds 不可变 reason。故采用 release+reserve 方案。`buyer_funds_hold_id` 指向新 order_fulfillment hold。

**卖方保证金方案**：卖单创建时预占全量 `fulfillment_deposit`（fund_holds reason=order_fulfillment_deposit）。撮合按已成交数量切分：release 原全量 hold，reserve「已成交部分保证金」hold（reason=order_fulfillment_deposit，记 seller_deposit_hold_id）+ reserve「剩余未成交保证金」hold（原 reason）。卖单若全量成交则原 hold 全切走。

> 这些 release+reserve 都在同一短事务内，账本总额/冻结不变，只是 hold 归类变化，可审计。撤单时释放「剩余未成交」hold。

### `application/order-service.ts`（修改 + 新增 match 用例）

新增 `match(input: { skuId, idempotencyKey?, requestId, now? }): MatchResult`：
1. `inventory.withLedgerTransaction` 内：
2. idempotency 检查（系统 actor = `system:match:<skuId>`，key 由调用方传）——并发第二次返回 in-progress。
3. 加载 skuId 下所有 `open`/`partially_filled` 买卖委托（`MATCHABLE_ORDER_STATUSES`，未过期）。
4. 构造 `MatchOrderInput[]`（含 sequence = rowid 单调序），调 `matchOrders()` 纯函数得 `legs` 与 `remaining`。
5. 对每个 leg（同一事务内顺序处理）：
   - 自成交已由规则跳过（leg 不含自成交对）。
   - **乐观锁推进订单状态**：用条件 UPDATE `WHERE id=? AND version=? AND remaining_quantity>=legQty` 扣减双方 remaining，`changes!==1` 则该 leg 跳过（并发已被其他撮合消耗）。
   - 转换买方资金：release 买方原 order_buy hold → reserve 已成交部分 order_fulfillment hold + reserve 剩余 order_buy hold。`buyer_funds_hold_id` 记新 hold。
   - 转换卖方库存：对卖方原 inventory_hold capture 已成交数量（库存离开卖方池，待履约）。`seller_inventory_hold_id` 记原 hold。
   - 转换卖方保证金：release 原全量 → reserve 已成交部分 + 剩余。`seller_deposit_hold_id` 记新 hold。
   - INSERT `bilateral_trades`（status=matched_pending_fulfillment，唯一约束防重复）。
   - 若订单 remaining 归零 → 状态 `matched_pending_fulfillment`；否则保持 `partially_filled`。
   - 写审计 `bilateral_order.matched`（买/卖各一条，或按 trade 一条）。
6. 返回 `MatchResultDto`（含本次 trades）。**不写 `p2p.trade.settled`、不动最终所有权**。

`create()` 末尾（提交前）记录需要撮合的 skuId，事务提交后调用 `this.match(...)`（同一进程异步触发，错误不影响 create 结果）。HTTP 层在 create 成功后触发 match。

### `api/order-routes.ts`（修改）
- 新增 `POST /v1/orders/match`（admin 或系统触发；I19B 用 admin 角色便于测试与运维手动触发）——`requireRole("admin")`，body `{ skuId }`，带 `Idempotency-Key`，调 `OrderService.match`。
  - **或**：`POST /v1/orders/:skuId/match`，admin 触发。采用后者更 RESTful。
- create 成功后由 OrderService 内部自动调 `match`（系统 actor，无需 admin）。HTTP 创建端点不需改签名。

> 选择：新增 `POST /v1/orders/:skuId/match`（admin）供运维/测试显式触发；同时 `create()` 内部在事务提交后自动触发一次 `match(skuId)`（系统幂等键），保证新委托能即时撮合。
