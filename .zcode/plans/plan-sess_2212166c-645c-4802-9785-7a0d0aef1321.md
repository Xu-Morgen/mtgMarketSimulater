# 修复 Playwright E2E 57 个失败用例

## 诊断结论（已通过受控实验复现确认）

失败用例的根因有两类，与"后端反应慢"无关：

### 根因 A：Next.js dev 首次按需编译慢（2–6s）+ Playwright `expect` 默认 5s 超时
- 实测首次编译耗时：`/catalog` **4524ms**、`/inventory` 2126ms、`/packs` 2118ms 等。
- 测试中 `link.click()` 导航 + `expect(...).toBeVisible()`（5s 默认）的组合，在首次编译 >5s 时稳定超时；`page.goto()` 因自带 `waitUntil` 反而能过。
- **仓库已有既定解法**：`inventory.spec.ts`、`packs.spec.ts` 已用 `toBeVisible({ timeout: 15_000 })` 适配；其余失败用例未同步。
- 影响：catalog / inventory / packs / auth / decks / tournaments / price-sync / price-history / achievements / player-loop / orders / market 等绝大多数用例。

### 根因 B：daily-work-funding.spec.ts 漏 mock `/v1/dashboard`
- I27F 给 dashboard 页加了 `/v1/dashboard` 查询，但 daily-work-funding.spec.ts（I23F 所写）的 mock 未补。
- 对 mock-only 用户 `/v1/dashboard` 走真实后端返回 404 → "首页概览加载失败" → 每日资金卡片、"服务端日期"文本不渲染。
- 对比：`player-loop.spec.ts`（I27F）已正确 mock `/v1/dashboard`（第 37 行）。
- 影响：daily-work-funding.spec.ts 的 3 个用例。

---

## 修复方案（已与用户确认）

### 改动 1：根因 A — 全局提高 expect 超时（`apps/web/playwright.config.ts`）
在 `defineConfig` 中新增全局 `expect` 超时配置，将默认 5s 提升到 15s，一处覆盖所有用例：

```ts
expect: { timeout: 15_000 },
```

加在 `timeout: 30_000,` 之后。这样：
- 所有 `expect(...).toBeVisible()/toBeEnabled()/toHaveURL()` 默认等 15s，覆盖 dev 首次编译（最坏 ~6s）。
- 既有 `toBeVisible({ timeout: 15_000 })` 显式写法仍兼容（值相同，无冲突）。
- 不改 `timeout: 30_000`（单测总超时）保持不变。
- 不需要为每个失败用例单独加 `{ timeout }`，避免改动散落 10+ 个 spec 文件。

### 改动 2：根因 B — 给 daily-work-funding.spec.ts 补 `/v1/dashboard` mock
在 `mockDashboard` helper（第 26 行）内新增一条 `page.route("**/v1/dashboard", ...)`，返回与 `player-loop.spec.ts` 的 `overview()` 同构的 minimal overview DTO，确保 `OverviewCards` + `DailyWorkFundingCard` 所需字段齐全：

所需字段（来自 `OverviewCards`/`DailyWorkFundingCard` 渲染逻辑）：
- `balance: { total, available, frozen }`（money）
- `netWorth`（money 或 null）
- `dailyWorkFunding`：复用本文件已有的 `status()` 返回值
- `todayTournaments: { availableCount, registeredCount, settlingCount, settledCount }`
- `collection: { distinctSkuCount, totalCardCount, marketValue, unpricedSkuCount }`
- `marketIndex: { referenceIndex, gameIndex, quotedSkus, capturedAt }`
- `todos: []`、`capturedAt`

money 用 `{ amount, currency: "GAME_CREDIT" }`。overview 包一层 `{ overview: {...} }`，再用 `envelope(...)` 包成响应包络，与 player-loop 第 37 行写法一致。

## 不做的事
- 不改业务代码、不改路由守卫、不改 Next.js 配置（关闭 dev 编译优化等）——根因是测试时序，不是产品缺陷。
- 不删任何测试、不放宽业务断言。
- 不引入 global-setup 路由预热等新机制——全局提超时已足够，且最小改动。
- 不改 `narrow-chromium` project 配置——它复用同一份 spec，改动 1+2 后自动受益。

2. `pnpm exec playwright test --project=narrow-chromium` → narrow-chromium 全绿。
3. 抽查 `auth.spec.ts:4`、`catalog.spec.ts:14`、`daily-work-funding.spec.ts:31` 三个代表性失败用例单独跑通。
4. 同步更新 `progress/`（若对应迭代有总结文件）与受影响文档（README 测试章节如有提及超时约定）——此条在实施时确认是否需要。
