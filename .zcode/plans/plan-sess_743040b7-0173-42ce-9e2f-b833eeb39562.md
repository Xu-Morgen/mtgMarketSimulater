## I35B 留存钩子与成长线服务端 — 实现计划

严格按《完整项目迭代实施计划与检查清单》I35B 的 3 个 checklist 项落地。用户已确认两项设计决策：
1. **任务奖励采用显式领取**（进度由已结算事实推进 → `claimable`，玩家经幂等命令领取，账本入账+状态机防重复）。
2. **等级解锁能力服务层生效**（NPC 每日交易额度倍数、批量开包上限随等级提升，在结算点强制执行）。

进度推进方式取舍：任务进度与等级同步在**已结算事实写入的同一 SQLite 短事务内同步推进**（不新增 job 类型），原因：① 等级需在 NPC 交易/批量开包结算点即时生效，异步任务会滞后；② 外层经济事务已保证 at-most-once，进度 upsert 用 max 语义 + `(user_id, definition_id, period_key)` 唯一约束收敛重放；③ 四个事实写入点（pack.open / npc.trade.settled / p2p.trade.settled / tournament.settled）已存在，各加一处跨模块 application 调用。

### 1. 迁移 `0037_retention_tasks_levels.sql`

- `task_definitions(id PK, period CHECK('daily'|'weekly'), metric_type CHECK('pack.open'|'npc.trade'|'collection.value'|'tournament.play'|'set.completion'), target_amount>0, reward_amount>0, title, description, rule_version, created_at)`，种子行由 `packages/rules resolveDailyTaskDefinitions` 固定（每日：开包 3 包/交易 10 张/NPC 卖出 1 次/收藏价值 2000；每周：参赛 3 场/任一系列完成度 80%）。沿用 `achievement_definitions` 风格（rule_version 列而非 rule_versions 行）。
- `task_instances(id PK, user_id→users, definition_id→task_definitions, period_key TEXT（daily=YYYY-MM-DD / weekly=ISO 周键）, current_value>=0, status CHECK('pending'|'claimable'|'claimed'), claimed_at, claimed_idempotency_key, updated_at, UNIQUE(user_id, definition_id, period_key))` + `(user_id, period_key)` 索引。自然日/周重置即新 period_key 新实例（旧实例只读保留，不删不重置）。
- `player_growth(user_id PK→users, total_xp>=0, level>=1, title, peak_net_worth_amount>=0, rule_version, updated_at)`。`settled_trades` 不落库（由表直接聚合）。
- `rule_versions` 插入 `daily-task/v1`、`level/v1` 定义 JSON（`ON CONFLICT DO NOTHING`）。
- 文件头注释 `-- I35B：...`；遵循既有 TEXT PK/整数/CHECK/索引/UTC 约定。

### 2. packages/rules

- `daily-task-rules.ts`：`DAILY_TASK_RULE_VERSION = "daily-task/v1"`；`DailyTaskDefinition`/`TaskPeriodKind`/`TaskMetricType`；`resolveDailyTaskDefinitions(version)`（不匹配抛 RangeError）；`evaluateTaskProgress({ruleVersion, metricType, targetAmount, profile})` 纯函数按类型计算贡献值（pack.open=npc.trade=数量加总、tournament.play=场次、collection.value=价值、set.completion=系列最高完成度 bp）。
- `level-rules.ts`：`LEVEL_RULE_VERSION = "level/v1"`；`LEVEL_THRESHOLDS`（1:0/2:200/3:500/4:1000/5:2000，封顶 5 级）；`resolveLevelExperience({ruleVersion, peakNetWorthAmount, settledTrades, collectionCompletion})` → `{totalXp, level, title, nextLevelXp, progressBasisPoints}`（XP = `floor(peak/1000)*20 + trades*5 + 80%系列数*10 + 100%系列数*50`，可重放）；`resolveLevelCapabilities(level)` → `{npcDailyTradeMultiplier, bulkPackMax}`（1:1/10、2:1/50、3:2/100、4:3/100、5:5/100）；`resolveLevelUpRewards(version)` 每级固定 GAME_CREDIT（2:200/3:300/4:500/5:1000）。
- `index.ts` 追加 `export * from "./daily-task-rules.js"`、`export * from "./level-rules.js"`。
- 单元测试：定义解析、各 metric 进度正常/边界/未知版本、XP 分级与封顶、能力表、奖励表、确定性重放。

### 4. growth 模块 `apps/api/src/modules/growth/`

- `domain/period.ts`：`dayPeriodKey(now, timezone)`（复用 `naturalDateAt`）与 `weekPeriodKey(now, timezone)`（ISO 周，`YYYY-Www`），纯函数。
- `application/task-service.ts`：
  - `advanceFromFact(factRow)`：由已写入的 fact（4 种）解析 userId（p2p 从 `bilateral_trades` 取买卖双方）与 occurred_at 周期键；对匹配 metric 的定义计算贡献并 `INSERT ... ON CONFLICT(user_id,definition_id,period_key) DO UPDATE SET current_value = max(current_value, excluded)`（claimed 实例跳过；`status` 达目标自动 pending→claimable）。
  - `overview(userId, now)`：今日+本周实例（LEFT JOIN 定义补 0 进度空态）+ pendingRewardCount。
  - `claim({userId, instanceId, idempotencyKey, requestFingerprint, requestId})`：幂等键 + 条件 `UPDATE ... SET status='claimed', claimed_at=?, claimed_idempotency_key=? WHERE id=? AND user_id=? AND status='claimable'`（changes=0 → 无此实例 404 / 已领取幂等成功 / 未达标 409 RULE_VIOLATION）；同事务 `creditAvailableFunds(reward, correlationId='task-reward:{userId}:{instanceId}', 'task_reward')` + 审计 `task.claimed` + 幂等完成。
- `application/level-service.ts`：
  - `syncForUser(userId, now)`：读 `accounts.total_amount` + 持仓按最新报价估值 → peak= max(现值)；`settledTrades = count(npc_trades)+count(履约 bilateral_trades)`；collection 里程碑读 `achievement_progress`（set-completion 定义，max 值不回退）；`resolveLevelExperience` → 若 level 上升：为 level+1..newLevel 各发 `resolveLevelUpRewards` 奖励（creditAvailableFunds，correlationId=`level-up:{userId}:{level}`）+ 审计 `level.up`；upsert player_growth（XP/level 只升不降）。幂等：level 已持久化不重发。
  - `capabilities(userId)`：读 player_growth（无行=1 级）→ `resolveLevelCapabilities`。
  - `profile(userId, now)`：先 `syncForUser` 再返回 GrowthProfileDto。
- `api/growth-routes.ts`：`GET /v1/growth`、`GET /v1/tasks`（player 角色，需存档，无存档 409「请先创建游戏存档」）、`POST /v1/tasks/:instanceId/claim`（player，幂等键，映射 conflict/in-progress/replayed 语义）。
- `api/growth-routes.test.ts`：事实推进进度/跨日周期键重置/每周键/claimed 冻结、collection.value max 语义、领取幂等/重复领取/越权 404/未达标 409、等级上升发放不重复、无存档 409。

### 风险与取舍
- 同步推进使 4 个结算事务略增写量，但保持 at-most-once 原子性；若未来任务逻辑膨胀可改为独立 `retention.process` job（迁移成本低）。
- 等级能力服务层生效改变低等级玩家批量开包/交易额度上限（F5 目标本身），level 1 默认与既有行为一致。
- XP 单调性依赖：peak 净资产 max-更新、settled_trades 表聚合、收藏完成度读 achievement_progress（max 不回退），全部不因卖出/消费降级。
