## 特殊点

- 权威边界：履约/取消履约只提交 `{ tradeId }` 空请求体 + 幂等键，所有费用、保证金、限价与成交价差额全部由服务端 I20B 的事务结算（`OrderService.fulfill`/`cancelTrade`）；浏览器不结算、不推导余额/库存/保证金、不复制可结算算法。`TradeConfirmDialog` 与摘要展示的待履约资金拆分（买方=数量×成交价+order_fee、卖方=已成交保证金）只读服务端 `PlayerBilateralTradeDto.pendingFunds`，不做本地汇总。成功响应里的 `trade: BilateralTradeDto` 携带对手身份（buyer/seller user IDs、双方 holdIds），前端只取 `status`/`updatedAt`/`id` 重建玩家视角 `PlayerBilateralTradeDto`，不把对手身份写入页面状态。
- 幂等与防重复：`useFulfillTradeMutation`/`useCancelTradeMutation` 与 `useCancelOrderMutation` 语义一致——`intent.current` 仅依赖 `tradeId`（服务端指纹 `orderTradeRequestFingerprint({ tradeId, action })` 也只依赖路径与动作），同一成交的网络重放返回首次结果、换成交才生成新键；组件层 `tradeActionLock` ref 在同一事件循环内拦截 React `disabled` 渲染前的第二击，与 I18F 的 `confirmationLock` 一致。已 fulfilled/cancelled 的成交由服务端状态机兜底返回 `RESOURCE_CONFLICT`，前端显示原因并提示刷新，不伪造成功。
- 无实体物流边界：为满足 I20F「界面明确不涉及实体物流」验收，弹窗与摘要两处声明「本市场为模拟卡牌市场，成交后的确认/取消是游戏内经济结算动作，不涉及实体卡牌物流、发货或退货」，对应契约 `BilateralFulfillmentType = "simulated"`（I20B 已定，本期补 contracts 单测固定取值）。到期回收在前端表现为「已取消」「不可操作」，与后端 `order.expire` 推进一致。
- 账本/审计入口：成功横幅附「关联成交 ID」（成交 `id`）；玩家首页 `/dashboard` 账本流水按 `correlationId`（履约 `p2p-buy`/`p2p-sell`、取消 `p2p-deposit-forfeited:{tradeId}`）核对关联条目即可追溯，本迭代未新增独立的成交详情/审计只读页（属管理端 AT-09/AuditModule 范围，非 I20F 范围）。
- 延后项：撮合风控（价格边界/频率/自成交标记，I21B）；P2P 端到端一致性恢复回归与运营手册（I22B，order.expire 已可工作但全链路恢复回归属 I22B）。
