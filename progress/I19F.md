## 特殊点

- 权威边界：`GET /v1/orders/trades` 与 `OrderService.listPlayerTrades` 是纯只读查询，不改经济真相、不写审计、不引幂等键；玩家视角 DTO 脱敏对手 userId、对手 orderId 与所有 holdId（`buyerUserId`/`sellerUserId`/`buyOrderId`/`sellOrderId`/`buyerFundsHoldId`/`sellerInventoryHoldId`/`sellerDepositHoldId` 均不返回），符合 AGENTS.md §6 安全约定。撮合顺序、成交价与部分成交语义仍全部位于 `packages/rules` 的 `order-matching/v1`，Orders 模块不复制可结算算法；卖方待履约资金（已成交保证金）由 JOIN 卖单委托的 `unit_fulfillment_deposit_amount × quantity` 推导，与 I19B 撮合写入的 `seller_deposit_hold` 金额一致。
- 契约与脱敏：`PlayerBilateralTradeDto` 与 I19B 的 `BilateralTradeDto` 并列——后者（含双方 userId/orderId）仅供 admin 撮合结果（`MatchResultDto`）与审计，前者（脱敏、附玩家角色）是玩家可见的唯一投影。`bilateral_trades` 表无需迁移，本期复用 I19B 已建表。
- 轮询与断线：`useOrderBookQuery`/`usePlayerTradesQuery` 玩家在线时 10s 轮询、`refetchIntervalInBackground:false`（切后台不轮询）、查询失败时不轮询（避免风暴）；组件层据此显示「数据可能过期，连接失败，正在重试」与「立即刷新」，恢复后只接受服务端最新状态、不伪造空态或最新状态，满足 I19F「刷新/轮询只接受服务端状态，连接失败时提示数据可能过期」。
- 缓存失效：订单簿失效已在 I18F 的 `useCreateOrderMutation` 中；本期为其与 `useCancelOrderMutation` 都补上 `["orders","trades",user.id]`（cancel 另补 `["orders","book",user.id]`），确保挂单/撤单后成交与订单簿查询随服务端响应刷新。
- 延后项：履约确认/取消（I20B/I20F）、`p2p.trade.settled`、最终所有权转移、卖方收入/保证金结算、`order.expire` 定时回收（I22B）不在本期；玩家页面的待履约资产只可展示、不可操作。
- 验证：已通过 `pnpm --filter @mtg-market/contracts test`（5 测试，新增 1）、`pnpm --filter @mtg-market/api test`（96 测试，新增 4）、`pnpm -r test`（contracts/rules/database/api/ai/web 全绿）、全 workspace `pnpm check`（eslint + 各包 tsc --noEmit）。Playwright `tests/e2e/orders.spec.ts` 桌面与 390 × 844 窄屏 22 项全绿（I18F 14 + I19F 8）。
- 已知限制（非本期引入）：`tests/e2e/catalog.spec.ts` 与 `tests/e2e/packs.spec.ts` 在本沙箱环境因 Ant Design `<Modal>`/`<Descriptions>` 遮罩层拦截点击而偶发失败；已分别通过临时回退 `.dialog` CSS 与 `orders-page.tsx` 之外的全部改动复跑确认其与本迭代无关（这些用例不访问 `/orders`，使用 Ant `<Modal>` 而非本项目的 `.dialog` 类）。`.dialog` 增加 `max-height`/`overflow-y:auto` 的改动反而修复了 I18F 窄屏弹窗双击「确认挂买单」被挤出视口的既有脆弱性。
